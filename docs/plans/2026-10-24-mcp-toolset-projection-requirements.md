# MCP toolset projection requirements

Status: source-side projection architecture selected and implemented in the
P08 candidate. The current authored contract has no HTTP operations, so its
generated public tool roster is empty by design. Operator-request models remain
schemas, not implicit tools or handlers.

## Context

The contract bundle records source and toolchain provenance, named request and
parameter schemas, exact status/body schemas, byte bounds, and explicit
`internal` or `public` exposure (`tools/contracts/FORMAT.md`). The qualified
generator currently refuses all public operations: its `public_mcp_tools`
function documents that public tool mapping is unspecified and returns an
empty list only when every operation is internal (`scripts/contracts/generate.py`).
This specification defines what a later, separately reviewed positive
projection must satisfy.

EC-00 qualification artifacts are disposable experiments. They are not the
production source of operations or tool meaning
(`docs/experiments/ec00-qualification/README.md`). Contract and owner sources
remain authoritative; projection adds a representation only.

## Decided requirements

### Selection and operation-to-tool mapping

1. The bundle manifest is the only input to projection. Only operations whose
   manifest exposure is exactly `public` are candidates. An `internal`
   operation never appears in tool metadata or a callable mapping.
2. Mapping is explicit, finite, and part of the reviewed source metadata. Every
   selected public operation maps to exactly one tool, and every tool maps back
   to exactly one operation. No tool is inferred from paths, HTTP verbs,
   generated SDK method names, or schema titles. No operation is omitted
   silently and no operation receives multiple aliases.
3. The projection mapping identifies the contract ID and version, operation ID,
   tool name, title, and description. Mapping keys must equal the selected
   public operation-ID set exactly. Duplicate operation IDs, duplicate tool
   names, or duplicate tool identities refuse the complete projection.
4. The public tool name is an explicit stable identifier matching the selected
   MCP name grammar; it is not generated by case conversion. Titles and
   descriptions are explicit, non-empty bounded text. They describe the
   operation's domain purpose and constraints without claiming authorization,
   success, or effects beyond the owner contract. These fields are projection
   metadata, not executable instructions or authority.
5. Projection is all-or-nothing for the selected mapping. Missing mapping
   entries, extra entries, unknown operation IDs, duplicate names, or a mapping
   to an operation marked internal refuse the projection. Unknown future
   metadata fields refuse rather than being ignored.

### Input schema and argument binding

6. Each projected tool has an `inputSchema` derived from the operation's named
   request-body schema and declared parameter schemas. The generated schema
   validates the tool's complete argument object, with no defaults, coercion,
   field dropping, or guessed optionality.
7. Binding rules are explicit and reversible:
   - A required path parameter is a required top-level argument under its
     declared parameter name.
   - A query parameter is a top-level argument under its declared name;
     requiredness is preserved exactly.
   - Header parameters are not caller-supplied tool arguments. Protocol,
     identity, and transport headers are outside the tool schema. Any
     operation with a domain header parameter is ineligible until an owner
     decision defines a safe binding.
   - If a request body exists, its JSON object properties are the top-level
     tool arguments. Body-property names may not collide with path or query
     parameter names. Their requiredness and schema constraints are preserved.
   - If the body schema is not an object, a single reserved `body` argument
     carries that JSON value. It may not collide with a parameter name.
   - If no body exists and there are no path/query arguments, the schema is an
     empty object. An absent body is never synthesized as `null`, `{}`, or
     empty text.
8. The binding plan records which input fields bind to path, query, or JSON
   body, and their source schema IDs. It never exposes an arbitrary header,
   URL, HTTP method, or transport option to the caller. Unbound arguments,
   ambiguous binding, duplicate names, unsupported parameter serialization,
   or a body/parameter collision refuse.
9. Only the operation's input contract is projected. Responses, response
   schemas, status codes, and transport errors do not become tool arguments.
   Tool execution and result projection require separate contracts and review.

### JSON Schema limits and validation

10. `inputSchema` uses JSON Schema 2020-12 and a closed top-level argument
    object. It is built from the authenticated schema bundle and named
    references; it does not fetch remote resources, resolve external or
    fragment references, or interpret annotation keywords as validation rules.
11. Projection supports only schema forms accepted by the existing finite
    contract profile. Any unsupported keyword or semantic form, unresolved or
    undeclared `$ref`/`$id`, recursive or ambiguous binding, or incompatible
    schema dialect refuses the entire mapping. The supported subset must be
    stated and versioned before implementation; an emitter's ability to
    produce a schema does not establish support.
12. `additionalProperties` behavior and required-property sets remain exactly
    as authored by the owner schema. Projection must not make closed command
    schemas open or closed metadata schemas more restrictive. No filtering,
    default insertion, type coercion, or validation bypass is permitted.
13. Tool input values obey the existing cross-runtime wire limits, including
    Unicode scalar strings and JavaScript-safe integer-valued JSON numbers.
    Values requiring larger exact integers use the owner-defined decimal-text
    representation. The request byte bound and JSON parser resource bounds
    remain enforced at execution; MCP schema metadata does not replace them.

### Provenance and deterministic output

14. Every emitted mapping is bound to the exact contract ID/version, manifest
    digest, schema-bundle digest, source digest, toolchain digest, and projection
    requirements version. Digests use canonical lowercase SHA-256. Projection
    inputs must be the exact bytes whose inventory was verified; rereading
    mutable files after integrity validation is forbidden.
15. The same reviewed inputs produce byte-deterministic tool metadata and
    binding plans. Output contains no inferred source, environment, owner, or
    runtime data. Any drift in inputs, output inventory, or provenance refuses
    publication of the projection artifact.

### Refusal and non-authority boundaries

16. Refusal is closed and atomic: malformed mapping data, duplicate or unknown
    operations, internal-operation selection, missing operation coverage,
    unsupported schema features, invalid names/text, or invalid provenance
    yields no partial tool list.
17. This is a definition-only projection. It grants no permission, supplies no
    credentials, and makes no assertion that an operation is reachable or
    authorized. Existing owner and service authorization remain mandatory at
    invocation.
18. This specification defines input metadata only. It does not define or
    authorize authentication, grants, handlers, dynamic tool listing, runtime
    discovery, installation, deployment, or public availability. A positive
    tool list requires a public OpenAPI operation plus its exact `mcpTools`
    entry in that operation's source `contract.json`; it does not infer a
    handler or bypass the owner authorization used at invocation.

## Selected architecture and current roster

These choices are implemented in the P08 candidate and are not blocked on an
additional owner decision:

- Only OpenAPI operations emitted from an authored owner TypeSpec source are
  eligible; existing models and client method names are not operation evidence.
- The public roster is the exact set of operations whose source exposure is
  `public`. Each requires an explicit stable tool name, title, and description
  in `contract.json`; mapping coverage is complete and all-or-nothing.
- Path and query parameters are top-level arguments. Object request properties
  are top-level arguments when the body schema is explicitly closed; non-object
  bodies bind to `body`. Header parameters, collisions, open body objects, and
  unsupported object keywords refuse the entire projection.
- The generator's finite JSON Schema 2020-12 profile and transitive local
  resource closure define supported input schema vocabulary. The generated
  `mcp-tools.json` is provenance-bound and included in the package inventory.
- Tool metadata does not select credentials or authorize invocation. Runtime
  dispatch must use the existing caller identity and owner operation path.

The current `contracts` source imports the operator-request model library but
does not define any HTTP service operations. The deliberate output is therefore
an empty tool list. The P08 change does not invent routes for the existing
`work.request.*` RPC methods. Adding a future public operation is a normal source
change: define it in TypeSpec, set its exposure to `public`, and provide its
exact mapping in the same owner's `contract.json`. No separate approval gate is
part of this projection architecture.

Names must never be derived from operation IDs or promoted from `internal`
exposure. Each emitted tool remains bound to the exact source, toolchain,
manifest, and schema-bundle digests.
